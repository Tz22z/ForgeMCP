# Architecture

## Design constraints

ForgeMCP treats reliability, context efficiency, and tool confinement as runtime
properties. A prompt can encourage behavior, but it cannot enforce a call budget,
prevent path traversal, or prove that the post-edit test suite passed.

The implementation therefore places those responsibilities below the model adapter.

## One run

1. `AgentRuntime` creates a run ID, append-only event journal, state machine, and budget
   ledger.
2. `RepositoryIndex.refresh()` hashes discovered files and reparses only changed
   content. Symbol extraction prefers Tree-sitter and falls back to Python AST.
3. `ContextSelector` scores candidates from issue terms, symbols, imports, dependents,
   recent diffs, test/source pairing, and any previous failure location.
4. `OpenAIResponsesModel` receives the issue, compact context bundle, hard limits, and
   strict function definitions.
5. `ToolDispatcher` validates arguments, reserves budget, checks policy, records the
   request, invokes one narrow tool, bounds its observation, and journals the result.
6. Edits invalidate and refresh the index. Test failures influence the next retrieval
   pass. A passing test marks only the current mutation generation as verified.
7. The final `RunResult` contains status, usage, changed paths, normalized test evidence,
   patch, and event-journal location.

## State and completion

```text
created → indexing → planning ⇄ acting
                         ↑        ↓
                         └── verifying
                               ├── succeeded
                               ├── failed
                               └── budget_exhausted
```

The runtime does not trust a model's final text as completion evidence. If the model
finishes after an unverified edit, ForgeMCP injects a test call. A failure returns its
bounded output and refreshed failure-local context to another planning turn.

`mutation_generation` increments after each successful file mutation.
`verified_generation` advances only after a passing test command. Completion requires
the two values to match.

## Index lifecycle

The SQLite index has four logical tables:

| Table | Purpose |
| --- | --- |
| `files` | Hash, language, size, line count, parser provenance |
| `symbols` | Named declarations and source ranges |
| `imports` | Dependency edges used for consumer expansion |
| `file_reads` | Per-content-version reads used for efficiency metrics |

Refresh is content-hash based. Timestamps are stored for observability but do not decide
whether parsing is skipped. This avoids both unnecessary parsing after a metadata-only
change and stale entries when timestamps are preserved.

After an edit, the dispatcher deletes the changed file's index record, identifies
importing consumers, and refreshes. The next selection therefore observes the new source
and can boost consumers that may need a coordinated change.

## Context strategies

`baseline` scans all files, performs lexical matching, and packs whole files. It models
a straightforward repository tool loop.

`hybrid` combines:

- path and issue-term overlap;
- exact and partial symbol matches;
- files importing a matched symbol's module;
- files changed in the recent Git window;
- source/test name pairing; and
- traceback-style `path:line` locations.

Large files are sliced around focus lines. Packing stops at a conservative UTF-8 token
estimate. API-reported usage, rather than this estimate, is charged to the run ledger.

## Model boundary

`ModelBackend` is a small protocol returning normalized decisions and usage. The OpenAI
adapter uses the Responses API and converts provider function calls into `ToolCall`
models. Tests use deterministic sequence models; this is why the control loop and demo
can be validated without network access or model variance.

The model never receives Python callables, a shell, or raw filesystem access. Its action
space is the JSON schema generated by `ToolDispatcher.definitions()`.

## Tool boundary

Dispatch order is deliberately fixed:

1. Find a known tool name.
2. Validate arguments against a strict schema.
3. Reserve budget and reject excessive repetition.
4. Evaluate approval policy from the tool's risk level.
5. Journal the sanitized request.
6. Execute the handler without a shell.
7. Bound output and retain a full observation reference if truncated.
8. Invalidate repository context after mutation.
9. Journal the typed result.

This gives one auditable place to add authentication, organization policy, or human
approval without changing model prompts.

## Isolation modes

Local mode is convenient for trusted development repositories. Docker mode constructs a
container call with network disabled by default, CPU/memory/PID caps, no capabilities,
no privilege escalation, read-only root storage, and a bounded no-exec `/tmp`.

`GitWorktreeManager` can allocate a detached worktree per task so concurrent runs do not
share source mutations. A higher-assurance deployment should combine this with a remote
VM or microVM boundary and disposable credentials.
